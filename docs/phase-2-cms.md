# Phase 2: Strapi CMS and content migration

Strapi is pinned to **5.58.0**, with the same version for Users & Permissions and the Cloudinary provider. It is a separate JavaScript application in `server/cms/`. No frontend rendering or contact transport behavior changes in this phase.

## Local setup

Use Node 22 and npm:

```sh
npm run install:all
npm run setup:cms
npm run migrate:portfolio
npm run dev:cms
```

Setup refuses to overwrite an existing `.env`. This checkout already has generated local secrets and the migrated SQLite database; do not rerun setup here. Open `http://localhost:1337/admin` and create your first Strapi administrator. No administrator password is embedded in source or generated by the migration. The built-in admin uses Strapi admin RBAC, separate from content-API users and the future custom `/admin` dashboard.

The client and Express API continue to use `npm run dev` and `npm run dev:api`. They do not depend on CMS availability until phase 3. Stop the CMS before running imports, backups or restores. Do not point a development `.env` at production.

## Models and validation

The two primary collections are Category and Content. Strapi assigns stable document IDs. Category has a stable unique slug, registered template, fixed template cardinality, display order and visibility. Content has a required category, display order, optional project slug and one typed dynamic-zone payload. Draft & Publish is enabled for Content; complete private drafts are allowed, incomplete drafts are rejected.

In the built-in Content Manager, choose a Category and add its matching payload component. The custom category-driven form arrives in phase 4; mismatched component selections are rejected by the CMS now.

Eight templates are registered: Hero, Experience, Projects, Skills, Skill Groups, Education, Site Settings and Section Settings. Required text, typed media, repeatable highlights/details/technologies/galleries, dates, links and boolean fields are defined in `server/content-contract/index.js`. Hero has text/link/code-panel fields only. Profile media belongs to Site Settings. Skills relate to Content documents whose category template is Skill Groups. Skill groups must be published before referencing skills can be published, and cannot be unpublished while published skills depend on them.

`getFormMetadata()` returns a plain, browser-safe metadata copy with field requirements, approved values, nested component definitions and named conditional rules. Both CMS and the prepared Express validator import the same local npm package. Future Express services must supply real persisted-media/group resolvers; the shared validator fails closed for these fields without resolvers. Metadata contains no executable validation code or credentials.

Document Service middleware validates creates, merged updates, publishing and draft restoration. Changing categories revalidates the destination payload/cardinality. Category template/cardinality cannot change when content exists; category slugs remain stable; used categories cannot be deleted. Inverse category relation edits and cloning are blocked so they cannot bypass content validation. In-use uploads cannot be removed or replaced; upload a new file and update the entry instead. This protects drafts and published versions alike.

Every portfolio mutation takes a transactional database row lock before checking invariants and writing. This serializes singleton creation, project slug checks, category changes and protected media changes across processes, rather than relying on an unprotected count. Draft and published versions with the same document ID count as one singleton. SQLite development uses one pooled connection; PostgreSQL uses the same transactional row-lock mechanism. PostgreSQL execution has not been tested in this environment.

Strapi's Content Manager in the installed 5.58.0 package calls Document Service for create/update/publish/delete/discard operations, including bulk actions through individual document calls. Integration tests exercise the actual manager service and authenticated REST writes. Internal Query Engine/raw SQL operations bypass Document Service and are reserved for trusted code; tests simulate legacy corruption to verify publication rejects invalid persisted data.

Content-API Category/Content permissions are denied for all Users & Permissions roles at bootstrap in this phase. Anonymous requests, including draft queries and writes, receive 403. Public account registration is disabled. An empty **PortfolioAdmin** content-API role is seeded for invite-only provisioning in phase 5; no users or passwords are provisioned and no public editing endpoints are introduced. Revisit the bootstrap permission lockdown when implementing phases 3 and 5.

## Repeatable import and backups

```sh
npm run migrate:portfolio
# Optional, only when intentional: publish imported content as well.
npm run migrate:portfolio -- --publish
```

The importer reads checked-in frontend data and approved JSX constants, including the hero's code-panel text, company-logo map, metadata, navigation, project introduction and contact copy. It imports 48 documents: Hero (1), Experience (3), Projects (5), Skill Groups (3), Skills (30), Education (4), Site Settings (1), Section Settings (1). It uploads 51 distinct source media files and preserves gallery order. The frontend remains on its existing local imports.

Migration keys identify logical entries across reruns; media source paths and SHA-256 content hashes identify reusable uploads. Repeating an import updates those drafts without duplicating entries/media. This deliberately restores source content over edits to imported drafts. It leaves unrelated content alone and does not delete old media. Existing unrelated singleton entries or conflicting slugs cause validation errors rather than replacement. `--publish` publishes groups first; publication status is distinct from a project's Live/Completed/In progress status.

Education and employment source dates have month precision and are stored as `YYYY-MM` strings. Year-only credentials remain completion years (2026 and 2020); no exact days are invented. A date accepts valid month or day precision. Image alternative text is generated from project names where the source has none. Redis is present in the source skill list but has no original icon mapping, so a simple text-label SVG in `server/cms/assets/redis.svg` supplies its required image. Existing frontend assets and design are unchanged.

Before initializing/importing, the CLI creates an ignored `.backups/before-import-<timestamp>/` snapshot. SQLite uses the native online backup API, and local uploads are copied alongside it. PostgreSQL requires a working `pg_dump` and creates a custom-format dump; import aborts if backup fails. External Cloudinary/Strapi Cloud media needs an independent provider backup. Production imports additionally require `--allow-production` and a backed-up media provider. Keep backup folders private.

To restore a local snapshot, stop CMS, preserve the current database/uploads as another backup, then copy the snapshot `data.db` and `uploads/` into their configured locations and restart. PostgreSQL restores use `pg_restore` into the intended environment only, together with provider media recovery. Never copy development secrets, database or media into production accidentally.

## Production separation

Set separate production `APP_KEYS`, salts, administrator JWT secret, content-API JWT secret and encryption key. `npm run build:cms` builds the admin UI; `npm run start:cms` runs it. Production startup requires PostgreSQL via `DATABASE_CLIENT=postgres` and `DATABASE_URL`, with verified TLS by default. Use the Strapi Cloud included database when hosted there.

Media defaults to local `public/uploads` for development. For Strapi Cloud included persistent media, set `STRAPI_CLOUD=true` on that platform. For another host, set `UPLOAD_PROVIDER=cloudinary` with its server-only credentials. Production local storage is rejected unless the Strapi Cloud flag is explicitly set. The database stores media metadata/references, not image binaries. CMS admin CSP permits the configured Cloudinary image/media domains.

This phase adds independent CMS npm commands and adjusts the Express Docker context to include the shared contract. CMS container orchestration and final three-service production deployment remain in phase 5. Docker, remote PostgreSQL and live Cloudinary/Strapi Cloud operations were not executed here. The CMS dependency installation currently reports 37 transitive npm advisories (5 moderate, 32 high); no breaking forced audit updates were applied to the pinned Strapi stack.

## Verification

- Strapi admin production build succeeds on Node 22.16.0.
- Built-in admin HTTP smoke test serves its HTML and JavaScript bundle. Private CMS secrets are absent from the built browser assets.
- Actual SQLite-backed CMS tests cover required/whitespace fields, wrong category/component, unknown media fields on Hero, missing/wrong/deleted media, conditional dates, failed-write rollback, concurrent duplicate Hero creation, category immutability/deletion/reassignment, duplicate project slugs, built-in editor and authenticated direct REST validation, signup/anonymous denial, publication revalidation, media removal/replacement and referenced group protection.
- Migration runs twice without duplicate documents/media and preserves document IDs, gallery order, typed images and year-only education. The local development database has been imported as private drafts with pre-import backups.
- Root `npm test` runs the existing 9 contact tests plus the CMS integration suite. `npm run test:cms` targets CMS only. No dev server is used to check types.
- Final results: 9 contact tests and 9 CMS tests pass; root lint passes with the 8 existing client warnings. The CMS syntax command checks 24 JavaScript files and schema JSON. The local database and retained backup each contain 48 logical drafts, zero published rows and 51 media records.
